01 · Skill 基礎

Skill 是 Claude 可重複使用的工作指引

當同一類工作反覆出現，而你每次都要向 Claude 重述範圍、步驟、判斷方式或輸出標準，便可考慮把這些資訊整理成 Skill。

每次重新交代

每次重新說明規格

每次都要重新下指令。少說一項要求或漏掉一個例外，輸出便可能不一致。

存成 Skill

同一套規格反覆使用

Claude 可在相關任務中依循同一套工作方法，讓你把注意力放在新問題與必要判斷。

Skill 可能包含的內容

Skill 的內容可依工作需要調整

my-skill/
├── SKILL.md          # 必要：用途 + 工作方法
├── references/       # 選用：規範、基準、專案記憶
├── scripts/          # 選用：需要確定性執行的工具
└── assets/           # 選用：模板、素材

簡單的 Skill 可能只有一份 SKILL.md；較複雜的 Skill 可將規則、參考資料和腳本分開放置。只加入工作確實需要的內容。

R

重複

同類型工作會再次出現。

M

方法

你已有固定做法或明確的輸出規格。

J

判斷

你能說明可接受的成果，以及不能交付的情況。

案例 A · 簡單 · 教學示例

將會議筆記整理為可寄出的會後摘要

虛構教學案例

這個案例從簡單情境開始：把一段零散的會議筆記整理為可直接寄給團隊的會後摘要。重點在於將「幫我整理一下」這類模糊要求，拆成可重複執行、可驗收的規格。

每次重新交代

「幫我整理會議紀錄。要有決議、待辦、未解問題、下次會議；不要自己猜負責人或期限；提案不能當成已決定。」

存成 Skill 之後

之後提供會議逐字稿時，Claude 可依照 Skill 分類、套用格式、標示缺漏，並按既定規則檢查輸出。

案例 A 的規格

把「幫我整理」寫成 5 條驗收規則

1

輸出固定四類

依序輸出以下四類：已確認決議、待辦事項、未解問題、下次追蹤。前三類沒有內容時，保留區塊並標示「無」；下次追蹤沒有資訊時，標示「未指定」。

2

提案 ≠ 決議

只有筆記明確表示「決定、確認、同意採用」的內容才能列為決議；「可以研究、建議、考慮」都不能列為決議。

3

待辦事項需有三個欄位

每個待辦事項都要列出：事項、負責人、期限。原文未明確指出負責人或期限時，填寫「未指定」，不可自行補上人名或日期。

4

分類必須互斥

同一事項不得同時歸入「決議」與「未解問題」。各類別不能互相重疊，避免摘要出現矛盾。

5

明確標示缺漏

缺少的資訊要明確標示，不能省略。讀者應能從摘要看出仍缺少哪些資訊。

驗收測試

請 Claude 按 5 項指標檢查輸出

把這些指標寫進 Skill，讓 Claude 逐項檢查是否符合規格。

驗證標準 檢查內容 通過標準 驗證規則
格式完整率 4 個固定類別區塊是否全部存在？ 4 / 4 規則一：輸出固定四類。
分類錯誤 「研究邀請制」是否被錯放成已確認決議？ 0 次 規則二：提案 ≠ 決議。
分類衝突 同一資訊是否同時出現在彼此矛盾的分類區塊？ 0 次 規則四：分類必須互斥。
虛構資訊 是否明示缺漏？是否自行補上原文沒有的負責人、期限或日期？ 0 次 規則五：明確標示缺漏。
待辦事項欄位完整率 每個待辦事項是否都有事項／負責人／期限三欄？ 100% 規則三：待辦事項需有三個欄位。
再測一個邊界情況

將輸入中的「下次會議時間」刪除後，再執行一次。此時應輸出「下次追蹤：未指定」，不可自行猜測日期，也要保留這個區塊。這是後續「測試與改進」章節的最小練習。

案例 A 重點

先寫清楚怎樣才算完成

固定格式只是起點。要能重複使用，還需寫明分類規則、禁止事項、缺漏處理方式及明確的通過／未通過指標。

02 · 專業判斷

把工作中的判斷寫進 Skill

案例 A 的規則容易寫清楚，真實工作卻常有更多判斷。Claude 即使完成流程，仍可能產出你不會交付的結果。Skill 還需要寫下處理順序、取捨原則、例外、停止條件，以及失敗時應如何說明。

1

處理順序

哪些問題必須先處理，否則後續數字沒有判讀價值？

2

取捨原則

分數、速度、完整度與準確性衝突時，應優先考量哪一項？

3

不確定資訊

資料查不到、來源互相矛盾或證據不足時，應猜測答案，還是明確說明限制？

4

停止標準

達到什麼條件後，可以停止優化？

課堂小練習

想一件你會交給新人處理的工作。驗收時，你會快速檢查哪三項標準，卻從未寫下來？這些標準通常最值得寫進 Skill。

案例 B · 專業判斷

讓下一份 AI 報告少犯同樣的錯

真實專案

這個專案使用 AI 產出深度研究報告。主要風險在於，報告看起來完整，日期、數字或推論仍可能有誤。我把查核方法、修正方式和停止條件寫進品質檢查 Skill，避免同類問題重複發生。每次發現錯誤，都要判斷它是單次問題，還是往後每份報告都應固定檢查的項目。

只修這份報告

這次修正，下次仍可能出錯

改正錯誤數字能挽救這份報告，但沒有保留處理經驗。下次遇到同類問題，Claude 仍可能重複犯錯。

留下檢查規則

把這次錯誤納入固定檢查

時間線、單位或來源問題若重複出現，就應寫進 Skill。下一份報告會多一道檢查，不必再次從頭學習。

真實案例

第一輪審查就抓到 12+ 個問題

其中有兩類重大事實錯誤：產品時程寫錯，以及市場規模數字引用錯誤。

只修正這兩項內容，只能改善這份報告。品質 Skill 還要辨識錯誤類型，並決定下次應在哪個步驟檢查。

重點：修正報告處理當前問題；更新規則才能減少下次重複發生。
一份報告要能交付

完成四項檢查後，再判斷是否交付

1. 先確認檢查真的有執行

曾有一份正式報告完全略過品質流程，此時任何分數都不足以判斷品質。先確認查證與審查都已完成，再檢視結果。

2. 重要數字和時間線重新查

不要直接沿用原先的搜尋結果。改用另一種查法，以至少兩個獨立來源交叉確認，並重新計算衍生數字。只要查證失敗或重算結果不一致，就先修正，暫不交付。

3. 讓另一個審查角色只看完成稿

審查者不看撰寫過程，避免替原本答案找理由。審查者把問題分為事實錯誤、方法缺口和風格建議；只有具備證據且影響品質的問題才修正。

4. 問題只剩風格時，才考慮停止

第三輪仍發現重大事實錯誤時，不能停止。某一輪只剩風格建議，且沒有值得採用的實質修正時，才可判斷結果已接近可交付。

真實四輪審查紀錄

依剩餘問題判斷何時停止審查

輪次發現問題採用修正看到的變化
第 1 輪12+ 個約 6 個仍有重大事實錯誤，例如時間線和關鍵數字。
第 2 輪6 個4 個重大錯誤下降，開始剩研究方法與解釋方式的缺口。
第 3 輪4 個4 個繼續補方法與說明，仍有值得修正的內容。
第 4 輪3 個0 個只剩風格建議，沒有實質修正被採用，可以停止。

這項紀錄不表示每份報告都必須審查四輪。它說明合理的改善順序：先減少重大事實錯誤，再處理研究方法與解釋的缺口，最後才處理風格。若第三輪仍出現重大錯誤，就要回頭檢查前面的產出流程。

Skill 裡還保存哪些判斷？

五條報告品質檢查規則

這些規則直接影響報告是否符合交付標準。

01準確比高分重要修正後分數降低，也要保留正確答案＋

如果修正讓報告更符合事實，就保留修正。不能為了維持漂亮分數，把已知錯誤留在報告裡。

02無法驗證，就明確標示不知道的地方不要寫成已證實＋

只有單一來源、無法獨立確認的說法，要清楚標示限制。讀者需要知道哪些資訊已確認，哪些仍有不確定性。

03改一個數字，要連帶重算前後不能同時留新舊答案＋

基礎數字改了，相關比率、結論和後文引用都要一起重算、檢查。否則前面雖然改對，後面仍可能留著舊答案。

04同類錯誤再出現，就新增檢查不要只要求下次更小心＋

如果不同報告反覆出現時間線計算或單位混淆，就代表流程少了一道檢查。把新檢查寫回 Skill，讓下一次自動套用。

05先證明有需要，再增加規則避免 Skill 越寫越長卻沒有幫助＋

想到一個可能有用的改善，不代表現在就要加入。先用真實報告證明問題確實存在，再增加檢查，避免規則無限膨脹。

這份 Skill 的用途

記錄團隊如何驗收報告

A

先做什麼

先確認流程有跑，再查事實；先修重大錯誤，再談方法與風格；不能因為分數高就放過錯誤。

B

怎麼從錯誤學習

這次錯在哪裡 → 哪些內容要修正 → 是否重複發生 → 是否新增固定檢查。下一份報告可直接套用這些經驗。

案例 B 重點

寫下驗收判斷，讓團隊依相同標準交付

Skill 應保存容易出錯的地方、足夠的證據條件、不可交付的情況，以及停止標準。判斷越清楚，團隊越能穩定產出符合標準的結果。

案例 C · 自動化 · 真實系統

每天 08:20 啟動盤前重點流程

已完成端到端驗證

這個案例示範一項每天都要準時完成的工作。流程由人每天早上記得執行，改為系統依排程啟動、判斷能否交付，並在失敗時重試。課程重點是自動化設計，不涉及投資教學。真實流程先掃描台股與美股，各選出 10 檔，再查最多 20 檔的相關新聞，最後發送一則短訊到 Discord。

為何適合自動化

每天 08:20 由排程開始執行

盤前資訊每天不同，工作順序卻固定；延後處理也會降低價值。排程負責決定何時開始，Skill 負責說明怎麼做，以及什麼情況算完成。

系統依台股的成交活躍度、價格動能與籌碼，以及美股的成交量與漲跌幅，各選出 10 檔。先縮小範圍，再處理值得注意的標的。

03NEWS

替最多 20 檔補上相關新聞

Claude 接著搜尋近期新聞，補充「今天為什麼值得注意」。系統只把外部內容當成資料，不把網路文字當作系統指令。

04MESSAGE

濃縮成一則短訊

訊息上限為 1,900 字。內容過長時，先縮至每個市場前 8 檔，再刪減註記；系統不拆成多則訊息發送。

05DELIVER

真的送達，才記「今天完成」

訊息經 Discord 接收成功後，系統才留下今日成功標記，避免重複發送。發送失敗就不寫入標記，後續仍須重試。休假日沒有新資料的情況，依下方例外規則處理。

教材不展示 webhook、API 金鑰、實際股票名單與真實推播內容；這些不是理解自動化設計所必需的資訊。
例外處理

先訂出例外處理規則：何時仍可交付，何時必須重試

早上發生的事系統怎麼做團隊會看到什麼
台股資料暫時抓不到系統繼續處理美股資料，避免單一市場的問題中斷整份結果。團隊仍可收到可用內容，訊息會標示哪個市場的資料不完整。
週末或市場休假，沒有新資料系統不發送「今日熱股」訊息，完成檢查後記錄今日已完成；這種情況不需要送達確認。在這種情況下，完成檢查後沒有訊息是正常結果。。
訊息第一次送不出去系統不寫入成功標記，15 分鐘後重試；若仍失敗，60 分鐘後再試。短暫的外部服務異常時，團隊不需立刻介入。
連續 3 次都失敗系統停止重試，改送一次失敗通知，請人員接手。團隊可依明確條件接手處理。
這個案例如何整理 Skill 文件

一份說明正常流程，另外兩份記錄失敗經驗與日常維護

這個系統把資料分成三份文件：設計規則、過去的故障紀錄，以及日常檢查步驟。維護時可依問題找到對應的說明。

WHYArchitecture Contract正常流程與必須遵守的設計規則＋

例如：有發送訊息時，只有真正送達才算成功；台股或美股單邊失敗時，另一邊仍可交付；秘密金鑰不得出現在程式碼或日誌。這份文件記錄系統不可違反的設計規則。

PASTFailure Archaeology曾發生的問題與處理方式＋

文件記錄真實事故與修正方式。例如，這個案例的互動模式捷徑，在無人值守模式中未載入。遇到相似症狀時，先比對舊事故，再決定處理方式。

OPSOps Runbook今天沒收到訊息時的檢查順序＋

先檢查今天是否有成功標記，再查看排程程序是否仍在執行、日誌內容與重試次數。這份清單讓維運人員依序檢查。

真實故障紀錄

第一個無人值守版本在 12 秒後結束，沒有錯誤訊息或任何產出

1. 表面看起來「有啟動」

排程確實啟動 Claude，但 12 秒後結束，沒有推播，也沒有今日成功標記。

2. 成功標記可辨識未完成的工作

執行過與送達成功是兩件事。沒有成功標記，代表今天的工作尚未完成。

3. 根因在無人值守模式的任務載入方式

這次故障的原因是：互動畫面可用的外掛（plugin）捷徑，在無人值守模式中未載入。Claude 實際收到空任務，因此很快結束。

4. 修正方式是明確指定任務內容

排程不再依賴互動捷徑，改為明確指定要讀哪份 Skill、依哪些步驟執行；並加入自動測試，避免日後改回會失效的寫法。

脆弱的自動化

排程啟動後，就視為工作完成

遇到假日、部分資料失敗或外部服務短暫故障時，團隊難以分辨正常未發訊息與系統故障。

可維運的自動化

每種狀態都有處理步驟

系統在正常時送達並留下標記；沒有新資料時完成檢查但不發訊息；部分資料失敗時交付仍可用的內容，並標示缺漏；發送失敗時重試；連續失敗時通知人員接手。

案例 C 重點

自動化前，先說清楚完成條件與失敗處理

Skill 寫清楚正常流程、部分失敗時的處理方式、重試規則與成功標準後，排程才能接手每天的啟動工作。這套設計可用於具有相同條件的業務流程。

收尾

選一件值得做成 Skill 的工作

  • 這項工作還會再發生嗎？
  • 我是否一直重複說明相同規格？
  • 其中是否有「我知道，但新人未必知道」的判斷？
  • 我能否說清楚哪些情況不能交付？
  • 若它同時具備高頻率、時間敏感、流程固定，是否值得自動化觸發？
先找出值得保存的工作方法，
再決定是否建立 Skill。
